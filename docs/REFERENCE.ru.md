# longrun - справочник

Версия 0.5.1. Проверено на Claude Code 2.1.238 (CLI) и 2.1.260 (desktop) на macOS; линуксовая половина слоя платформы (таймеры systemd и cron, файл кредов, выбор программ диалога и уведомления) проверена на Ubuntu 24.04 с python3 3.12, там же зеленые все четыре набора тестов. Раздел 12. Факты о хуках и приложении сняты с живых запусков и сверены с официальными доками; сырье в [research/VERIFIED.md](../research/VERIFIED.md) и [research/hook-payloads/](../research/hook-payloads/).

## 1. Сущности

- **Проект** - каталог `.longrun/`. Общая память всех сессий, которые стартовали внутри проекта или в каталоге, привязанном к нему. Имя проекта - имя родительской папки (`shop`), либо ключ `name` в `config.json`.
- **Сессия** - один разговор Claude Code. Ключ сессии - первые 8 символов ее первого CLI id. Принадлежит одному проекту: связь записывается на `SessionStart` в `~/.claude/longrun/sessions/_index/<CLI id>.json` и дальше все хуки идут по ней, а не по cwd (cwd в payload хука - это cwd шелла после `cd`).
- **Каталог** - где сессия стартовала. Определяет проект: вверх по дереву до `.longrun/` (каталог или файл-указатель с путем в первой строке), иначе `~/.claude/longrun/registry.json` по самому длинному совпавшему префиксу. Каталог ничего не хранит.

### Как разрешается идентичность сессии

| Событие | Что делает longrun |
|---|---|
| `SessionStart` с известным CLI id (компакция, resume из CLI, `/clear` без смены id) | тот же ключ, что в `_index` |
| Новый CLI id, у которого в файле приложения есть `priorCliSessionIds` (resume в приложении; приходит как `source=startup`) | ключ предыдущего id из цепочки; все, что успело записаться под новым id (например, журнальная строка от `watch`), сливается в каталог цепочки |
| Новый CLI id с `source=clear` | ключ сессии, которая закончилась с причиной `clear` в том же cwd не позднее трех минут назад |
| Новый CLI id, у которого приложение еще не записало метаданные | пока свой ключ; на каждом ходу хук перечитывает файлы приложения, и как только цепочка видна, перепривязывает сессию и один раз показывает ее свои заметки с пометкой "continued from CLI id ..." |
| `source=fork`, в файле приложения есть `forkedFromSessionId` | свой ключ, свои заметки родителя копируются один раз |

Файлы приложения: `~/Library/Application Support/Claude/claude-code-sessions/*/*/local_*.json` (macOS; на Linux `$XDG_CONFIG_HOME/Claude/...`, `LONGRUN_DESKTOP_DIR` переопределяет оба), поля `sessionId` (стабильный id записи в сайдбаре), `cliSessionId`, `priorCliSessionIds`, `forkedFromSessionId`, `title`, `cwd`, `isArchived`, `lastActivityAt`. На 07.09.2026 у 193 из 210 записей `cliSessionId` не совпадает с `sessionId`, а цепочка `priorCliSessionIds` есть у пяти: id приложения - его собственный, а не бывший CLI id.

## 2. Файлы и форматы

### Проект `<root>/.longrun/` (или `~/.claude/longrun/projects/<slug>/` при `--external`)

| Файл | Формат |
|---|---|
| `NOTES.md` | заголовок и строки `- [n<id>] MM-DD <tag> (<автор>): <текст>`. Автор - заголовок сессии из сайдбара (до 24 символов), иначе имя каталога. Чужие строки (ручные правки, `## заголовки`) сохраняются как записи без id |
| `ledger.md` | `- [L<id>] open|waiting|blocked|done @<owner> MM-DD: <текст> [| next:YYYY-MM-DD] [| URL]`. Ручные строки не переформатируются и не нумеруются |
| `inbox/*.md` (и `inbox/` в каталоге сессии, см. watch) | `<ts>-msg-to-<адрес>-from-<sid8>.md` (сообщения сессиям; адрес - `d<8 символов id приложения>` или `sid8`), `<ts>-report-<scope>-<sid8>.md`, `<ts>-ask-...`. Доставленные и подтвержденные уезжают в `inbox/.archive/` |
| `config.json` | переопределения настроек проекта, см. раздел 6 |
| `state.json` | `next_note`, `next_ledger`, `last_gc` |
| `archive/compact/<ключ сессии>-<ts>.md` | резюме компакции дословно, включая блок `<analysis>`, которого нет в транскрипте |
| `archive/precompact/<ключ>-<ts>.md` | снимок перед компакцией: текст `/compact ...`, последние просьбы пользователя длиннее 40 символов, правленые файлы, FAIL-строки |
| `archive/notes.md`, `archive/ledger.md` | удаленные, замененные и состарившиеся записи, по строке с полной датой; строки с пометкой `legacy <путь>` - заметки хранилищ worktree версии 0.2 |
| `archive/sessions/` | `<ключ>.journal.md` (обрезанные хвосты журналов) и `<ключ>/` (каталоги сессий, молчавших дольше `session_dead_days`) |

### Сессия `~/.claude/longrun/sessions/<ключ проекта>/<ключ сессии>/`

Ключ проекта - путь каталога проекта с не-буквенными символами, замененными на `-` (последние 90 символов).

| Файл | Формат |
|---|---|
| `notes.md` | как `NOTES.md`, но `[s<id>]` и без автора |
| `journal.md` | `MM-DD HH:MM <строка>`; строки от `longrun log` помечены `* `; механические: `session <source>`, `FAIL \`<команда>\` -> Exit code N ...`, `compaction ...`, `summary archived ...`, `send -> ...`, `watch wN ...`, `session end (<reason>)` |
| `meta.json` | `sid` (текущий CLI id), `skey`, `cwd`, `scope`, `started`, `last_seen`, `ended`, `tools`, `turns`, `edit_tools_since_note`, `fails`, `files` (правленые), `compactions`, `last_status` (первые 200 символов последнего ответа, хук `Stop`), `permission_mode`, `desktop_id`, `shared_seen` (id -> хеш текста общих записей, которые сессия уже видела), `last_note` |
| `state.json`, `archive/notes.md` | счетчик id своих заметок; удаленные свои записи |

### Глобальное `~/.claude/longrun/`

`registry.json` (`links`: каталог -> каталог проекта), `config.json` (глобальные переопределения), `sessions/_index/<CLI id>.json` (`local`, `cwd`, `skey`, `at`), `watch/` (`w<N>.json`, `env.json` со снимком PATH, `state.json`, `run.log` и лог самого планировщика: `launchd.log`, `systemd.log` или `cron.log`).

## 3. Команды

Коды выхода: 0 ok, 1 не найдено / проверка не прошла, 2 неверные аргументы или бюджет, 3 нет проекта или сессии, 4 команда слоя HQ при выключенном слое.

### Настройка

- `longrun init [--external] [--hq|--no-hq]` - сделать cwd проектом. `--external` кладет каталог под `~/.claude/longrun/projects/` и регистрирует cwd в `registry.json`. `--hq` включает ledger и inbox. Повторный вызов только меняет флаги.
- `longrun link <root | root/.longrun>` - сессии, стартующие в cwd, относятся к этому проекту. Пишет только в `registry.json`. Каталог проекта должен уже существовать. Хранилище версии 0.2 в этом cwd, если было, сворачивается: его заметки уходят в `archive/notes.md` проекта, файл переименовывается в `NOTES.legacy.md`.
- `longrun unlink` - убрать запись из реестра, ничего не удаляя.
- `longrun where` - проект, режим, сессия и ее каталог.

### Заметки

- `longrun add [--shared] -t dead|decision|fact|ctx|todo|pin [-s <автор>] "<текст>"` - одна строка до 400 символов. Без `--shared` - в свои заметки (нужна известная сессия: `LONGRUN_SESSION` из окружения сессии либо самый свежий heartbeat с тем же cwd). Дубликат по тексту не добавляется. При переполнении - код 2 и список кандидатов на удаление.
- `longrun rm s3 n12 ...` - удалить; строки уходят в архив. Число без префикса считается своей заметкой.
- `longrun replace s3|n12 "<текст>"` - переписать; старый текст в архив.
- `longrun notes [--shared | --own | --session <кто>]` - показать; по умолчанию оба файла.
- `longrun prune [--auto] [--shared]` - кандидаты на удаление (дешевле всего `todo`, затем `ctx`, `fact`, `dead`/`decision`; `pin` не трогается); `--auto` архивирует до 60% бюджета.
- `longrun log "<веха>"` - строка в журнал сессии.
- `longrun compact-hint [--set "<текст>" | --clear]` - что хук `PreCompact` скажет суммаризатору сохранить (раздел 4), напечатанное ровно в том виде, в каком уйдет; `--set` добавляет одну свою строку от этой сессии, `--clear` ее убирает. То же самое на весь проект - `longrun config set compact_instructions "..."`.
- `longrun recall <слово> [...] [-n 12] [--no-transcript]` - поиск. Порядок: общие и свои заметки, ledger, чужие свои заметки и журналы, inbox, архивы; затем транскрипты проекта (`recall_transcripts` штук, свежие первыми, плюс транскрипты сабагентов текущей сессии). Транскрипт - внутренний формат Claude Code, парсер защитный: при смене формата совпадений станет меньше, падения не будет.

### Сессии

- `longrun status [--all]` - сессии проекта: ключ, имя, состояние (`alive`, `alive+sock`, `stale Nm`, `active?`, `ended(reason)`), scope, число своих заметок, счетчики, последний ответ. Сессии без ходов, вызовов, заметок и ответов скрыты как шум приложения. Плюс бюджеты, ledger и inbox при HQ.
- `longrun send [--list] [--inbox] [--resume [--max-turns N] [--model M] [--mode <permission mode>] [--timeout S]] <кто> "<текст>"|-` - адресат: заголовок из сайдбара, имя из реестра Claude Code, id или его префикс, `local_<id>`. Работает - конверт в его сокет; не работает - файл в inbox проекта адресата (не отправителя); `--inbox` - всегда файлом; `--resume` - `claude -p "<текст>" --resume <id>` в cwd адресата, ответ печатается. Неоднозначное имя - отказ со списком.
- `longrun important [on | next | N | off] [--to <кто>]` - пометить сессию, конец хода которой нельзя пропустить: пока флаг стоит, уведомление уходит независимо от `notify_turn_end` и от того, какое окно в фокусе. `on` держится до `off`, `next` взводит один конец хода, `N` - счетчик, который тратится по одному за ход и сам снимается на нуле. Без аргумента печатает флаг этой сессии и все остальные помеченные сессии проекта; `--to` принимает те же имена, что и `send`. Флаг лежит в `meta.json` сессии (`important: {mode, left}`), поэтому переживает компакцию, `/clear` и resume, и виден флагом в `status` и в шапке дайджеста.
- `longrun report - | "<текст>"`, `longrun inbox [ls | show <часть> | ack <часть>... | ack --all]`, `longrun ledger ...`, `longrun ask "<текст>"` - слой HQ.

### watch

`longrun watch add [--to <кто>] [--every 5m] [--for 7d] [--wake [--wake-mode M] [--wake-turns N]] [--no-notify] [--no-test] --then "<что сделать>" -- <проверка>`

| Проверка | Условие выполнено |
|---|---|
| `pr-merged <id|ветка>` | PR влит. GitHub: `gh pr view --json state` в репозитории, откуда зарегистрирован watch; Arcadia: `arc pr status --json` из `arc_root`. Инструмент выбирается при регистрации (ключ `pr_tool`: `auto` смотрит на папку, `.arc` -> arc, `.git` -> gh) и записывается в проверку. `closed`/`discarded` - жесткая ошибка |
| `pr-status <id|ветка> <open|merged|closed>` | статус равен заданному (`discarded` = `closed`) |
| `at 'YYYY-MM-DD HH:MM' | HH:MM | +2h` | момент наступил (HH:MM в прошлом = завтра) |
| `file /путь` | файл существует |
| `http URL [--expect ТЕКСТ] [--token-file ~/.tokens/x] [--auth-scheme OAuth]` | ответ 2xx и, если задано, содержит текст; 401/403/404 - жесткая ошибка, остальное - "еще нет" |
| `cmd '<shell>'` | код 0 = выполнено, 1 = еще нет, 3 = сдаться. Абсолютные пути, без alias, без Touch ID и ssh: запускается таймером с PATH, снятым с шелла при `add` |

Под таймером macOS интерпретатор может не иметь доступа к `~/Documents` (TCC): чтение конфига такого проекта тогда дает пустой конфиг, а файл сообщения пишется во второй inbox `~/.claude/longrun/sessions/<проект>/<сессия>/inbox/`, который хуки читают наравне с inbox проекта (`delivered.how` = `session-inbox:`). Ошибка доставки любого другого рода записывается в запись watch (`delivered.how` = `error: ...`) и в уведомление на рабочем столе, состояние сохраняется, тик продолжает работу: watch не повисает в pending и не стреляет повторно.

Поведение: проверка запускается сразу (`--no-test` отключает): уже верно - ничего не регистрируется; жесткая ошибка - отказ. Далее тик раз в `--every` (не чаще самого таймера, 5 минут). Три жесткие ошибки подряд - состояние `broken`, срок `--for` вышел - `expired`; в обоих случаях адресат получает одно сообщение. Доставка: сокет, если адресат работает; `claude -p --resume` при `--wake`; иначе файл в inbox. Плюс уведомление на рабочем столе. Запись хранит стабильный id приложения адресата, поэтому переименование и resume ничему не мешают. Другие подкоманды: `ls [--all]`, `rm <id>`, `test -- <проверка>`, `sessions`, `run [--force] [id]`, `install [--every 5m]`, `uninstall`, `status`.

### Служебные

`longrun digest [--source startup|compact|...]` (что печатает хук), `longrun gc` (уборка сейчас), `longrun hook <Событие>` (вызывается хуками, JSON на stdin), `longrun help`, `longrun rules`, `longrun version`.

`longrun onboard` печатает бриф для первого разговора о скилле: что делает, нюансы, состояние машины (проект, таймер, окно автокомпакции в Claude Code против ключа `autocompact_window`) и список настроек, о которых стоит спросить пользователя, с текущими значениями и смыслом. Агент пересказывает его на языке пользователя, спрашивает по одной и применяет ответы через `config set`; `longrun onboard done` записывает `onboarded_at` в глобальный конфиг, после чего дайджест перестает подсказывать `longrun onboard`.

`longrun config` показывает действующие настройки и откуда каждая взята (default / global / project); `longrun config set KEY VALUE` пишет в `config.json` проекта, с `--global` в `~/.claude/longrun/config.json`; `longrun config unset KEY [--global]` возвращает значение по умолчанию. Тип значения проверяется по умолчанию ключа (число, дробь, true/false), незнакомый ключ отклоняется.

## 4. Хуки

Одиннадцать записей в `~/.claude/settings.json`, все вызывают `longrun hook <Событие>`. Проект резолвится по `_index` для всех событий, кроме `SessionStart(startup|resume|fork)`, где он резолвится по cwd и записывается в `_index`. Вне проекта хук молча выходит с кодом 0.

| Событие | Что делает | Что печатает в контекст |
|---|---|---|
| `SessionStart` (все источники) | привязка CLI id к сессии (цепочка resume, `/clear`, fork), heartbeat, строка в журнал, экспорт `LONGRUN_SESSION`, `LONGRUN_DIR`, `LONGRUN_SCOPE`, `LONGRUN_TRANSCRIPT` через `CLAUDE_ENV_FILE`, раз в час gc, отметка "все общие записи показаны" | дайджест (раздел 5) |
| `UserPromptSubmit` | счетчик ходов; дочитывание метаданных приложения и перепривязка цепочки; при HQ раз в 5 ходов - пункты `@user` и просроченные `next:` | сообщения из inbox; свои заметки один раз при перепривязке; разница общих заметок; напоминание раз в 8 ходов без записи (только после правок или упавшей команды) |
| `PostToolUse` (Edit, Write, MultiEdit, NotebookEdit, Bash, PowerShell, Agent, Task, Workflow, mcp__*) | счетчики; правками считаются только четыре редактирующих тула; список правленых файлов | сообщения из inbox как `additionalContext`; напоминание раз в 40 вызовов |
| `PostToolUseFailure` (Bash, PowerShell; async) | строка `FAIL` в журнал, не больше `fail_keep` штук | - |
| `PreToolUse` (все инструменты) | при `halt` отказ `permissionDecision: deny` с причиной (кроме вызовов самого `longrun`); для Bash, PowerShell, Agent, Task, Workflow и MCP-тулов запись в `running` меты (команда, начало) | отказ с причиной при halt, иначе ничего |
| `PermissionRequest` (async) | `waiting_since` / `waiting_what = permission (<tool>)` в мете | - |
| `Notification` (permission_prompt, idle_prompt, agent_needs_input, elicitation_*; async) | ожидание подтверждения или ввода в мете; `idle_prompt` снимает `turn_started` | - |
| `PreCompact` | снимок в `archive/precompact/` | инструкции суммаризатору (ниже) |
| `PostCompact` (async) | резюме в `archive/compact/` | - |
| `Stop` | последний ответ в `last_status`; при `strict_stop` блокирует завершение хода с напоминанием | - |
| `SessionEnd` | причина в heartbeat, строка в журнал | - |

Порядок событий вокруг компакции: `SubagentStop` (суммаризатор) -> `SessionStart(compact)` -> `PostCompact`. Поэтому дайджест после компакции называет каталог архива, а не файл: текущее резюме ложится туда через мгновение после дайджеста.

### Как управлять самой компакцией

Автоматическая компакция и `/compact <текст>` собирают **один и тот же** промпт суммаризатора (тот самый, из восьми секций: запрос и намерение пользователя, технические понятия, файлы и код, ошибки и починки, решение задач, все сообщения пользователя, незакрытые задачи, текущая работа). Разница ровно одна: непустой текст инструкций приклеивается к нему в конец блоком `Additional Instructions:`. То есть автокомпакция - не другой, более глупый механизм, а тот же самый, только без подсказки, которую человек пишет руками.

Этим блоком становится stdout хука `PreCompact`. Проверено чтением Claude Code 2.1.238: результаты хуков с кодом возврата 0 и непустым stdout склеиваются через перевод строки в `newCustomInstructions`, мерджатся с тем, что пользователь написал после `/compact`, и уходят в сборку промпта; матчер срабатывает и на `trigger: "auto"`, не только на `"manual"`. Отсюда два следствия: текст не стоит контекста (его пишет скрипт, а не модель), и человеку больше не надо ловить момент перед компакцией, чтобы ею управлять.

`longrun` печатает его из `compact_hint()`: четыре постоянные строки (сохранить тупики вместе с причиной; сохранять точные строки, а не их описания; выкинуть то, что вернет один Read; сохранить формулировки самого пользователя), затем выведенное из состояния сессии - задачи этой сессии на доске, файлы, которые она правила, id заметок, которые и так переинжектятся сразу после компакции, - затем строка проекта `compact_instructions` и строка сессии из `longrun compact-hint --set`. При переполнении `compact_hint_max_bytes` первыми уходят выведенные строки (файлы, заметки, задачи, вводная), постоянное ядро и две человеческие строки остаются. `longrun compact-hint` печатает ровно то, что отправит хук; `compact_hint false` выключает все это.

Грабли: stdout, который разбирается как JSON, читается вместо этого как объект решения хука (а `decision: "block"` отменяет компакцию - сессия продолжается несжатой), поэтому текст простой; ограничение в 10000 символов на вывод хука действует и здесь; этот же текст показывается в транскрипте строкой результата хука.

## 5. Дайджест и бюджеты

Состав по порядку: заголовок `<longrun v… project=… session=<имя> [<ключ>] source=…>`; MESSAGE (недоставленные сообщения); `SHARED notes (project X) N entries used/cap`; `OWN notes (this session)`; `SESSIONS of project X` (до 6 других сессий: имя, ключ, состояние, scope, число своих заметок, последний ответ; живые первыми); `WATCH n pending`; `LEDGER open` и `INBOX` при HQ; `HANDOFF` (только после компакции: FAIL-строки, `FOCUS:` из `/compact <текст>`, `ASK:` последние просьбы, `FILES:`); хвост журнала (после компакции, resume, `/clear`, fork и при продолженной цепочке); строка про архив резюме; подсказка команд.

Бюджеты по умолчанию: общие заметки 5000 байт, свои 3000, ledger 3000, дайджест 9000 (лимит вывода хука в Claude Code - 10000 символов), блок сессий 700, HANDOFF 1100, разница общих заметок на ходу 1200. При превышении дайджест сбрасывает блоки в порядке: сессии, watch, журнал, HANDOFF, затем ledger сжимается до строк `@user` и просроченных, затем убирается; заметки не сбрасываются никогда. Нехватка места после всего этого - обрезка хвоста с закрывающим тегом.

Стоимость: дайджест 350-2000 токенов в зависимости от заполненности; на ходу - только разница и сообщения, обычно ноль.

## 7. Сообщения между сессиями (механика)

Реестр сессий Claude Code: `~/.claude/sessions/<pid>.json` (`sessionId`, `name`, `cwd`, `messagingSocketPath`). Живая сессия принимает на unix-сокете одну JSON-строку `{"msgV":1,"msg_id":…,"type":"user","message":{"role":"user","content":…},"priority":"next","from":"uds:…"}`; без `priority: "next"` простаивающая сессия ход не начинает. Тело обернуто в `<cross-session-message from-name=… from-mode=…>`, как делает собственный `SendMessage` Claude Code 2.1.260; получатель видит `Message from @<имя>` и сохраняет свои права. Формат взят из бинаря, не из доков.

Файл в inbox доставляют хуки адресата: `SessionStart` (в дайджесте), `UserPromptSubmit`, `PostToolUse` (`additionalContext`). Файл адресуется стабильным id приложения, когда он известен, поэтому переживает resume; хуки читают оба адреса. Сообщение кладется в проект адресата по `_index`, даже если отправитель в другом проекте.

`--resume`: `claude -p "<текст>" --resume <id> --max-turns N` в cwd адресата, из окружения убраны `LONGRUN_*` и `CLAUDE_ENV_FILE`, чтобы поднятая сессия привязалась к своему проекту. Без диалогов прав: годится "проверь и доложи", не "выкати".

## 8. Миграция с 0.2

Автоматически, при первом обращении:

- хранилище worktree (`~/.claude/longrun/projects/<slug>/` с `config.hub`) - проектом становится хаб; заметки старого хранилища уходят в `archive/notes.md` проекта с пометкой `legacy`, файл переименовывается в `NOTES.legacy.md`; запись реестра при следующем `longrun link` начинает указывать прямо на проект;
- плоские файлы сессий `<sid8>.json` и `<sid8>.md` раскладываются в `<sid8>/meta.json` и `<sid8>/journal.md`; каталог `sessions/` внутри проекта версии 0.1 переезжает туда же;
- заметки хаба остаются общими заметками проекта как есть (id `n…` не меняются); своих заметок у старых сессий нет, они появляются с первого `longrun add`.

Сессии, идущие в момент обновления, ничего не теряют: каждый хук сначала переносит файлы старой раскладки и только потом читает их, а если сессия уже успела записать что-то в новую раскладку, старое и новое сливаются (счетчики суммируются, строки журнала идут по порядку).

Что меняется в привычках: `longrun add` без `--shared` теперь пишет в свои заметки; карта PR и все, что нужно другим сессиям, - с `--shared`. `rm`/`replace` принимают `s3` и `n12`. Бюджет общих заметок 5000 вместо 6000.

## 10. Что гарантировано, что вероятностно, что сломается при смене версии

**Механикой:** заметки и журнал возвращаются в контекст на каждом `SessionStart`, включая компакцию, `/clear`, resume и fork (проверено на транскрипте); каждое резюме компакции архивируется целиком; упавшие команды попадают в журнал; бюджеты нельзя превысить через CLI; параллельные записи не теряются (`flock` + атомарная замена); сообщения доставляются один раз; разница общих заметок считается по хешам текста, а не по времени.

**Только вероятностно:** что модель напишет заметку, отметит `--shared` то, что нужно другим, вызовет `recall` вместо повторного исследования, будет удалять. Anthropic закрыл как not planned просьбу дать модели гарантированный ход перед компакцией (issue anthropics/claude-code#43733). Разделение с автопамятью держится на инструкции.

**Сломается при смене версии Claude Code:** формат транскрипта (recall, снимок перед компакцией: меньше совпадений, снимок короче); формат сокета и реестра сессий (`send` в живую сессию; очередь через inbox продолжит работать); формат файлов приложения (цепочка resume, разрешение имен из сайдбара; без них сессия после resume в приложении начнет с пустыми своими заметками, старые останутся на диске и в `recall`); имена полей событий хуков; лимит вывода хука 10000 символов; `CLAUDE_ENV_FILE` (без него сессия определяется по cwd, что ломается при двух сессиях в одной папке); подхват хуков на лету (проверен эмпирически, в доках не обещан).

**Не покрыто:** сабагенты дайджест не получают; Windows не проверялся (`fcntl`, unix-сокеты, ни один из трех планировщиков); `/rewind` заметки не откатывает; при resume в истории остаются два дайджеста до ближайшей компакции (поведение Claude Code); две сессии, сделавшие `/clear` в одной папке за три минуты, могут связаться не с тем ключом.

**Проще, если нужна только ре-инъекция:** строка `@.longrun/NOTES.md` в `CLAUDE.md` приезжает после компакции без хуков и без лимита вывода хука. Хуки нужны ради своих заметок, архива резюме, журнала падений, HANDOFF, сессий и сообщений.

| `halt "почему" [--project]`, `resume` | запрет инструментов во всех сессиях (или только в этом проекте) / снятие |
| `interrupt WHO [--match TEXT] [--yes] [--why TEXT]` | список Bash-процессов сессии (дети ее `claude` с оберткой shell-snapshot); `--yes` SIGTERM, через 1.5 с SIGKILL, запись в журнал цели и сообщение ей |
| `budget [status]` | правило, последняя выборка, ожидаемое и отношение, темп по истории, снооз, последний стоп |
| `budget check` | выборка сейчас (токен из Keychain через `/usr/bin/security` на macOS, из `~/.claude/.credentials.json` на Linux; эндпоинт `api.anthropic.com/api/oauth/usage`), вердикт и стоп при нарушении |
| `budget on|off`, `budget set pace|factor|quiet|every N` | глобальный конфиг `~/.claude/longrun/config.json` |
| `ask "вопрос" [--options "Да,Нет"] [--default Да] [--text] [--title T] [--wait SEC] [--expire MIN] [--icon note|caution|stop]` | диалог поверх всех окон (osascript из собственного процесса со звуком на macOS, zenity или kdialog на Linux); ответ инлайн, если пришел за `--wait` (по умолчанию `ask_wait_sec`), иначе `PENDING Q<n>` и ответ ходом в сокет или inbox; строки `ANSWER|CANCELLED|EXPIRED|FAILED Q<n>` |
| `ask ls`, `ask answer Q3 "..."` | вопросы этой сессии; записать ответ, который человек дал в чате, когда диалог пропал |
| `ask --ledger "..."` | прежний `ask` слоя HQ: пункт ledger на пользователе плюс отчет в inbox, без диалога |
| `mcp` | stdio MCP-сервер с тулами `ask` и `notify`; `install.sh` регистрирует его как `longrun` в user scope (`claude mcp add --scope user longrun -- ~/.local/bin/longrun mcp`) |
| `notify "text" [--title T]` | одно уведомление на рабочий стол - то же самое шлют `halt`, правило бюджета и сработавший watch; печатает, через какую программу ушло, и выходит с 1, если такой программы нет |
| `notify --test` | послать пробу и сказать, показал ли ее экран на самом деле: на macOS ответ читается из базы Центра уведомлений, а не угадывается. `presented=0` - доставлено и молча выброшено, и тогда в выводе написано, чем это чинится |
| `notify setup [--icon FILE]` | собрать бандл, от имени которого уходят уведомления, чтобы у них была наша иконка и имя `longrun`, а не terminal-notifier (только macOS; `install.sh` делает это сам) |

### Что видит каждая сессия

В дайджесте: строка `ORCHESTRATOR: <имя> [skey] alive|idle|stale|ended since ...`, блок `BOARD`, `YOUR TASK` для выданных задач, `HALT in force` при остановке, флаги в строках `SESSIONS`. На каждом ходу и после инструментов: `BOARD changes for you` (выданные и измененные задачи, новые факты по своим задачам; свои правки не повторяются), предупреждение `context Nk of the Mk auto-compact window` за `ctx_warn_before` до окна, один раз на 20k роста. Оркестратор дополнительно получает `role=orchestrator` в заголовке, блок `FACTS unhandled` и список обязанностей. Сессия, задавшая вопрос через `ask`, до ответа видит блок `ASKED, waiting for the user`, остальные - флаг `asking the user Q3 12m` в ее строке SESSIONS.

### Смотритель

Каждый тик после проверок `stuck_scan`: для каждого проекта с зеркалом оркестратора и живой ролью, для каждой сессии кроме оркестратора: инструмент дольше `stuck_tool_min`, ход дольше `stuck_turn_min`, ожидание подтверждения или ответа на `ask` дольше `stuck_wait_min`, `stuck_fail_streak` одинаковых FAIL подряд, контекст ближе `ctx_warn_before` к окну. Если у сессии есть живой pid, а в дереве процессов нет обертки shell-snapshot, флаг `tool` не поднимается (мета устарела). Каждый флаг сообщается один раз на эпизод: `STUCK? <имя> [skey]: ... Options: ...`, доставка в сокет (`wake_on_stuck`) или inbox.

### Окно контекста

`autocompact_window(model)`: `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, иначе `autoCompactWindow` из `~/.claude/settings.json` (его пишет `/autocompact 300k`), иначе окно модели (1M у Fable, Sonnet 5, Opus 5; 200k у остальных); не больше окна модели. Размер контекста = `input + cache_read + cache_creation` последнего ответа ассистента из хвоста транскрипта (256 КБ), та же формула, что у строки статуса.

### Бюджет 5-часового окна

Каждый тик после `stuck_scan`: `budget_scan` берет выборку не чаще `budget_check_every`, считает старт окна как `resets_at - 5h`, ожидаемое = план x часы с начала окна, нарушение = использовано >= `budget_factor` x ожидаемое, кроме первых `budget_quiet_min` минут. Нарушение при включенном правиле, без действующего halt и без снооза: `halt.json` с `kind: budget` на все проекты, отчет в файл, в сокет или inbox каждого оркестратора, уведомление macOS и диалог `STOP` с кнопками Keep stopped / Resume all (отвязанный процесс, тик его не ждет; Resume all = `resume` от имени человека). `longrun resume` после такого стопа ставит `snoozed_until = resets_at`. Ошибка источника (нет токена, диалог Keychain без ответа дольше 25 с, HTTP 401 при протухшем токене) пишется в журнал смотрителя один раз и стопа не вызывает. Токен не пишется ни в один файл. Подмена источника в тестах: `LONGRUN_BUDGET_FIXTURE=<json-файл>`.

### Диалог с человеком

`ask` показывает диалог той программой, которая есть у этой ОС (раздел 12). На macOS это `osascript` из собственного процесса: разрешение Automation не нужно, окно само выходит на передний план (проверено 09.09.2026), режим Focus прячет уведомления, а не окна; перед показом `beep`. До трех вариантов - кнопки `display dialog` (кнопка с именем Cancel и Esc дают `CANCELLED`), больше - список `choose from list`, `--text` добавляет поле. Вопрос регистрируется в `asks.json` и журнале, диалог держит отвязанный процесс `longrun ask _wait Q<n>` (setsid, переживает конец вызова Bash и MCP). Спросивший ждет ответ до `--wait` и возвращает его инлайн; по истечении снимает `claimed`, и процесс диалога сам доставляет ответ через `deliver_to`: сокет сессии (ход начинается сразу, даже посреди хода), иначе inbox, иначе spool. Гонка между ними закрыта общим замком сессии: ответ либо уходит инлайн, либо сообщением, но не пропадает. `--expire` (по умолчанию 360 мин) закрывает диалог сам (`giving up after`, для списка - таймаут процесса); неотвеченный вопрос в проекте с HQ становится пунктом ledger на пользователе.

MCP-сервер `longrun mcp`: JSON-RPC по stdio, одна строка на сообщение, без зависимостей; методы initialize, tools/list, tools/call, ping, остальное - ошибка -32601; вызовы тулов в потоках, чтобы отмена и второй вызов не ждали первого. Сессию находит по pid родителя в `~/.claude/sessions/<pid>.json` (сервер - дочерний процесс `claude`; обход до шести уровней вверх), проект - по индексу сессии, иначе по cwd; без проекта диалог показывается инлайн без поздней доставки. По документации Claude Code: таймаут MCP-тула по умолчанию около 28 часов, idle-таймаут stdio-сервера 30 минут без ответа, вызов дольше 2 минут в интерактивной сессии уходит в фоновую задачу; поэтому `wait_sec` ограничен 1500 с. Во время halt тулы `mcp__longrun__*` не запрещаются.

Переменные окружения для тестов: `LONGRUN_ASK_FIXTURE=<json {"button","text","state"}>` заменяет диалог, `LONGRUN_ASK_FIXTURE_DELAY=<сек>` задерживает ответ, `LONGRUN_NO_UI=1` запрещает настоящие диалоги и уведомления (без фикстуры `ask` отвечает `FAILED`), `LONGRUN_NO_TIMER=1` запрещает трогать launchd, systemd и crontab, `LONGRUN_DESKTOP_DIR=<каталог>` подменяет каталог метаданных приложения.

## 12. Платформа: macOS и Linux

Все, кроме четырех вещей, - обычный POSIX-питон без зависимостей, и работает одинаково. Эти четыре решаются в рантайме, один раз, по тому, что на машине реально есть.

**Таймер, который гоняет тик.** Его ставит `install.sh` (`--no-timer` пропускает), и первый `watch add` ставит его, если таймера нет; `longrun watch install` заводит то, что сказано в ключе `watch_timer`, а по умолчанию то, что дает эта ОС:

| ОС | Что создается | Где | Как посмотреть |
|---|---|---|---|
| macOS | агент launchd `com.longrun.watch`, `StartInterval`, `RunAtLoad` | `~/Library/LaunchAgents/com.longrun.watch.plist` | `launchctl print gui/<uid>/com.longrun.watch` |
| Linux с пользовательским systemd | `longrun-watch.service` (`Type=oneshot`) и `longrun-watch.timer` (`OnUnitActiveSec`, `OnBootSec=1min`), включается с `--now` и один раз запускается сразу | `~/.config/systemd/user/` | `systemctl --user list-timers longrun-watch.timer`, `journalctl --user -u longrun-watch.service` |
| Linux без него (контейнер, WSL1, голый `su`) | одна строка в crontab пользователя, помеченная комментарием, чтобы `uninstall` убрал ровно ее и ничего чужого | `crontab -l` | `longrun watch status` |

Любой таймер запускает проверку с почти пустым окружением, поэтому PATH снимается с настоящего шелла в `watch/env.json` при `add` и `install`; на Linux туда же попадают `DISPLAY`, `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR` и `DBUS_SESSION_BUS_ADDRESS`, чтобы уведомление из тика дошло до рабочего стола. Точность интервала: launchd догоняет пропущенные интервалы на пробуждении, `OnUnitActiveSec` считается по `CLOCK_BOOTTIME` и ведет себя так же, у cron просто пол в одну минуту. Пользовательский таймер systemd работает, только пока у пользователя есть сессия: на сервере без `loginctl enable-linger <user>` он останавливается при выходе, и `watch install` говорит об этом, если linger выключен.

**Диалог за `ask` и `mcp__longrun__ask`.** macOS: `osascript`. Linux: `zenity`, иначе `kdialog`, и только когда выставлен `DISPLAY` или `WAYLAND_DISPLAY`. Ни одна из этих программ не умеет кнопки и поле ввода одновременно, поэтому с `--text` на Linux побеждает поле, а кнопкой в ответе приезжает вариант по умолчанию. zenity раскладывает варианты на `--question` (`--ok-label` - вариант по умолчанию, `--extra-button` - средний), больше трех - на `--list`, и держит `--expire` своим `--timeout`; kdialog использует `--yesno` и `--menu`, а истечение срока у него - это убийство процесса. Машина вообще без диалога - сервер, сессия по ssh, не поставлен zenity - это не аварийное состояние: `ask` возвращает `FAILED Q<n>` с причиной, а скилл велит агенту спросить в чате.

**Уведомление на рабочем столе** - то, чем сообщают о себе `halt`, остановка по бюджету, сработавший watch и MCP-тул `notify`. Оно необязательно на обеих системах, и longrun не зависит ни от одной из этих программ: все, что несет уведомление, и так доезжает до самой сессии через ее сокет или инбокс, поэтому машина, где ничего не установлено, - поддерживаемая конфигурация, и все четыре набора тестов гоняются именно так. Программу задает ключ `notifier`; `auto` берет `terminal-notifier`, если он поставлен, иначе `osascript` на macOS и `notify-send` на линуксовом рабочем столе, иначе не берет ничего - и это нормальное состояние сервера, а не поломка: сообщение все равно доедет до сессии через сокет или инбокс.

terminal-notifier стоит первым из-за ловушки macOS, которую снаружи не видно. `osascript -e 'display notification'` отправляет уведомление от имени Script Editor, а у того нет собственного разрешения на уведомления (нет ключа `auth` в `com.apple.ncprefs`), поэтому macOS кладет уведомление в базу и не рисует ничего: проверено 10.09.2026, когда 25 из 25 уведомлений через osascript лежали в базе Центра уведомлений с `presented = 0`, а уведомления самого приложения Claude показывались нормально. Ошибки при этом не печатается нигде - `osascript` выходит с нулем. У terminal-notifier свой подписанный бандл, поэтому у него своя запись и свое разрешение; после `brew install terminal-notifier` бандл нужно один раз зарегистрировать (`lsregister -f` и один `open`), иначе он отвечает `Could not request notification permission`.

**Уведомление о конце хода.** Приложение Claude шлет его само, но с `silent: true` и `interruptionLevel: "passive"` - а это на macOS значит, что система кладет уведомление в Центр уведомлений, не подсвечивая экран, не проигрывая звук и не рисуя баннер. Всплывает только второй тип, `needs_input` ("Claude is waiting for your input"), он уходит как `active`. Настройки на это нет: `notificationLevels` самого приложения выбирает лишь `off | badge | banner` и на interruption level не влияет. Поэтому громкий вариант шлет `notify_turn_end` из хука `Stop`. Режим `unfocused` спрашивает у Launch Services (`lsappinfo front` - без Automation-разрешения и без запроса, в отличие от пути через `System Events`), какое приложение сейчас впереди, и молчит, пока это Claude. Сессия в терминале не знает, чье окно впереди, поэтому там `unfocused` работает как `always`. Проверено на Claude.app 2.1.260, 10.09.2026.

**Важные сессии.** Обе проверки выше глобальные, и у обеих одна слепая зона: пока вы работаете в одной сессии Claude, приложение в фокусе, поэтому `unfocused` молчит про *все* сессии - включая ту долгую, которую вы как раз ждете. `longrun important` помечает одну сессию исключением: хук `Stop` шлет уведомление независимо от `notify_turn_end` и от того, кто в фокусе, а заголовок начинается со звездочки, чтобы такое уведомление было видно среди остальных. У флага три формы - `on` (пока не снимут), `next` (один конец хода) и `N` (счетчик), - и лежит он в `meta.json` самой сессии, рядом со счетчиками: поэтому переживает компакцию, `/clear` и resume (ключ сессии идет по цепочке resume, а id из CLI - нет). Счетчик тратится внутри того же лока, который пишет мету хода, так что два хука гонкой не потратят его дважды, и каждая отправка пишется в журнал сессии вместе с программой, которая ее доставила, - или с `NOT sent: no notifier here`, если на машине уведомлений нет вовсе.

**Иконка и имя отправителя.** И то и другое берется из бандла, который отправил уведомление, и переопределить их у отдельного уведомления macOS не дает - именно поэтому в terminal-notifier 3.1.0 выключены `-appIcon` и `-sender`. Поэтому `longrun notify setup` собирает копию terminal-notifier.app в `~/.claude/longrun/notifier/longrun.app` со своим `CFBundleIdentifier` (`fr.julienxx.oss.terminal-notifier.longrun` - копия остается опознаваемой как копия), `CFBundleName` `longrun` и, по умолчанию, иконкой локально установленного Claude.app: уведомления эти про сессии Claude, а иконка берется из установки на самой машине и никуда не распространяется. `--icon FILE` принимает `.icns` как есть, а png или jpg конвертирует через `sips`. Правка подписанного бандла ломает подпись, поэтому копия переподписывается ad-hoc, регистрируется через `lsregister` и один раз открывается - именно первый запуск дает ей свою запись в System Settings и свое разрешение. `install.sh` делает это сам, когда terminal-notifier установлен, а `notify_user` предпочитает копию тому, что лежит в PATH.

**Куда ведет клик.** Уведомление longrun несет диплинк той сессии, о которой оно: клик открывает именно ее, а не просто поднимает окно - `claude://code/continue?session=local_<uuid>&source=desktop_action`. Схему `claude` регистрирует само приложение, а параметр проверяет регуляркой `/^local_[A-Za-z0-9-]+/` - это ровно тот id, который longrun и так хранит как `desktop_id`, и та же ссылка, которую приложение строит для собственных уведомлений. Нести цель клика умеет только terminal-notifier (`-open`); у osascript и notify-send такого нет, и ссылка просто отбрасывается. У сессии без записи в приложении (только CLI, или метаданные еще не записаны) ссылки нет, уведомление все равно уходит.

Все это делает за вас `install.sh`: на macOS он ставит terminal-notifier через brew, если его нет, собирает бандл и заканчивает одним тестовым уведомлением (первая отправка после свежего `open` всегда падает с "Could not request notification permission" и сама же создает запись разрешения, поэтому setup повторяет попытки, пока одна не пройдет); `--no-notify` пропускает всю эту часть. Проверка - `longrun notify --test`: он печатает цель клика и шлет пробу, а на macOS пробует вычитать флаг `presented` из `~/Library/Group Containers/group.com.apple.usernoted/db2/db`, а не гадает. `presented=1` - баннер действительно нарисовали; `presented=0` - доставлено и выброшено, и тогда печатается, чем чинить. База живет в режиме WAL, а система чекпойнтит ее лениво, поэтому она копируется вместе с `-wal` и копия открывается на запись, чтобы sqlite проиграл журнал; строки все равно может не оказаться (в таблице лежит то, что сейчас в Центре уведомлений, и система сама выкидывает записи) - тогда команда говорит, что ответа не знает, и просит посмотреть на экран.

**Собственный OAuth-токен Claude Code** (его читает только правило бюджета, в файлы и логи он не попадает). macOS: запись логин-кейчейна `Claude Code-credentials` через `/usr/bin/security`, с откатом на файл. Linux: `~/.claude/.credentials.json` (`$CLAUDE_CONFIG_DIR` учитывается) - файл, который Claude Code сам туда пишет. Нет кредов - правило бюджета молча выключается одной строкой в логе смотрителя, остальное работает как обычно.

Мелочи, решаемые тем же способом: метаданные приложения лежат в `~/Library/Application Support/Claude` на macOS и в `$XDG_CONFIG_HOME/Claude` на Linux (нет приложения вовсе - просто нет заголовков сайдбара, адресация по id сессии продолжает работать); запущенная проверка получает `LANG=en_US.UTF-8` на macOS и `LANG=C.UTF-8` на Linux; в снимок PATH дополнительно заглядывают `/home/linuxbrew/.linuxbrew/bin` и `/usr/local/sbin`.
