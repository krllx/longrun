# Оркестратор: сессия, которая ведет проект к цели

Статус: дизайн от 2026-09-08, этапы 1 и 3 реализованы 2026-09-09 (версия 0.4.0, раздел 11).
Опирается на проверенные факты из раздела 7, непроверенное помечено явно.

## 1. Зачем

Сейчас у проекта есть штаб, общие заметки и статус сессий, но человек сам ходит по
сессиям: спрашивает, что сделано, раздает пункты, замечает застрявшие процессы, следит за
контекстом и за расходом лимита. Текста при этом столько, что в голове он не держится.

Хочется одну сессию на проект, которая:

1. ведет короткий список "сделано / делается / осталось" в рамках цели;
2. раздает задания сессиям, заводит новые (или просит человека) и получает отчеты;
3. замечает затыки: инструмент крутится слишком долго, запуск уже не нужен, сессия ходит
   по кругу, ждет подтверждения, которого никто не видит;
4. держит контекст сессий ниже порога и заказывает компакцию с сохранением заметок;
5. следит за расходом 5-часового окна: если тратим в полтора раза быстрее плана, все
   останавливает и докладывает;
6. с уточнениями, сомнениями и решениями приходит к человеку через диалог поверх всех окон
   (в обход режима "не беспокоить"), а не ждет, когда он заглянет в чат;
7. принимает новые факты извне (коммент в ревью, сообщение в мессенджере, слова человека)
   даже посреди работы, фиксирует их и дальше решает уже с их учетом.

## 2. Сущности

| Сущность | Что это | Где живет |
| --- | --- | --- |
| Оркестратор | обычная сессия проекта, взявшая роль; одна на проект | замок `.longrun/orchestrator.json` (сессия, pid, с какого времени, цель) |
| Воркер | любая другая сессия проекта; ничего нового не учит, кроме `board take/done/block` | как сейчас |
| Доска | цель + задачи со статусами todo / doing (кто, с какого времени) / blocked (почему) / done (итог) / dropped | `.longrun/board.json`, рендер в дайджест каждой сессии |
| Смотритель | тик таймера `longrun watch`, уже есть; получает правила про затыки и бюджет | как сейчас |
| Спрашивалка | MCP-сервер `longrun-ask`: диалог поверх всех окон, ответ приходит в сессию ходом | новый, отдельный бинарь |

Замок берется командой `longrun orchestrate start --goal "..."`, вторая сессия получает отказ с
именем держателя. Замок протухает, когда сессия закончилась (SessionEnd) или pid умер, тогда
`start` в другой сессии его перехватывает. Дайджест воркеров показывает строку
`ORCHESTRATOR: <имя> alive since ...`, чтобы каждый знал, кому докладывать.

## 3. Что оркестратор видит: телеметрия без токенов

Все сигналы собирают хуки и смотритель в `meta.json` сессии, оркестратор читает их через
`longrun status` и свой дайджест. Модель воркера в это не вовлечена.

| Сигнал | Откуда | Как считается |
| --- | --- | --- |
| Контекст, % | транскрипт: `usage` последнего сообщения ассистента | `input + cache_read + cache_creation` делить на окно модели (1M у Fable, Sonnet 5, Opus 5; 200k у 4.6); пишет хук Stop/PostToolUse |
| Ход идет N минут | UserPromptSubmit ставит `turn_started`, Stop снимает | возраст метки |
| Инструмент крутится N минут | новый хук PreToolUse пишет `tool_started` + команду, PostToolUse снимает; плюс дерево процессов: дети pid сессии (pid есть в `~/.claude/sessions/<pid>.json`) | возраст метки, `etime` ребенка |
| Ждет подтверждения N минут | хуки `PermissionRequest` и `Notification(permission_prompt)` | не проверено, что в приложении они срабатывают (см. раздел 7) |
| Простаивает с задачей в doing | Stop без нового промпта дольше N минут при задаче в doing | по `last_seen` |
| Ходит по кругу | журнал: FAIL с той же командой 3 раза подряд | по журналу |
| Движение по доске | события `take / done / block` | пишет CLI |
| Расход 5-часового окна | раздел 6 | смотритель |

В блоке SESSIONS оркестратора это выглядит так:

```
PR D [dd4a4da6] alive, task T7 doing 2h10m, ctx 41%, tool `ya make ...` 38m, fail x3 same cmd
PR H [dda66bb1] stale 3h, task T9 doing, ctx 12%
Тестинг платежей [8a7610a4] alive, waiting permission 12m
```

Оркестратор не читает транскрипты воркеров: это раздувает его контекст. Для разбора одного
случая есть `list_events` приложения, по запросу.

## 4. Что оркестратор может сделать: рычаги

| Рычаг | Механизм | Состояние |
| --- | --- | --- |
| Написать воркеру | `longrun send`: живой сессии в сокет (ход начинается сразу), остальным в inbox (прочитается на следующем событии, токенов не стоит) | есть |
| Назначить задачу | `longrun board assign T7 <сессия>`: воркер видит `YOUR TASK` в дайджесте на следующем событии | новое |
| Спросить человека | тул `ask` спрашивалки: диалог поверх окон, ответ приходит ходом | новое, раздел 5 |
| Завести сессию | в приложении чип `spawn_task`: оркестратор оставляет кнопку с самодостаточным промптом, клик человека открывает сессию (клик и есть подтверждение); в терминале диалог или чат с готовой первой строкой `longrun take T7`; `claude --bg "..."` для самодостаточных задач без присмотра (документировано: супервизор, `claude agents --json` со `state` и `waitingFor`) | есть в Claude Code |
| Остановить всех | `longrun halt "причина"`: хук PreToolUse запрещает любой инструмент во всех сессиях аккаунта, причину видит модель; `longrun resume` снимает | новое, документированный `permissionDecision: deny` |
| Прервать инструмент | убить дочерний процесс инструмента у сессии; воркер через PostToolUseFailure получает "прервано оркестратором: причина" | новое, только с подтверждения человека, не проверено в приложении |
| Заказать компакцию | напрямую нельзя: слэш-команда в межсессионном сообщении приходит текстом и не выполняется (документировано). Порог держится окном автокомпакции: `/autocompact 300k` сохраняется в `autoCompactWindow` и действует на все сессии; хуки PreCompact/PostCompact longrun делают снимок и возвращают дайджест. Оркестратор заранее просит воркера записать заметки, а компакцию с кастомным промптом предлагает человеку одной кнопкой в диалоге | есть, порог задает человек |

## 5. Потоки

Оркестратор событийный, а не опрашивающий: он просыпается, когда что-то произошло, и
спит бесплатно в остальное время.

**Старт.** `longrun orchestrate start --goal "..."` берет замок, пишет цель, при желании
засевает доску из списка. Дайджест оркестратора: GOAL + BOARD + SESSIONS с флагами + INBOX,
без длинных заметок.

**Назначение.** Оркестратор выбирает следующий todo, назначает, воркер на следующем
событии видит задачу, берет `board take T7`, работает, закрывает `board done T7 "итог"`.
Хук Stop воркера отправляет событие оркестратору. Событие, требующее решения (done,
blocked, вопрос), будит оркестратора через сокет; остальное ложится в inbox.

**Задача есть, отдать некому.** Сам оркестратор сессий не открывает. В приложении он
оставляет чип `spawn_task`: заголовок - задача, промпт самодостаточный (что сделать и зачем,
первая строка `longrun board take T7` и `longrun link <корень проекта>` на случай, если
приложение откроет сессию в свежем worktree, где `longrun where` скажет not initialised).
Пока человек не кликнул чип, ничего не запускается, поэтому диалог перед ним не нужен; какие
чипы оставил, оркестратор называет в ответе. В терминале чипа нет: диалог или чат с первой
строкой для вставки.

**Затык.** Смотритель раз в 5 минут считает флаги из раздела 3. Правило сработало
(инструмент дольше 30 минут, ход дольше часа, три одинаковых FAIL, ожидание подтверждения
дольше 10 минут) -> сообщение оркестратору с пробуждением. Оркестратор решает: написать
воркеру, спросить человека, предложить прервать.

**Вопрос человеку.** Воркер ставит `board block T7 "вопрос"`. Оркестратор либо отвечает сам
из общих заметок, либо зовет `ask`. Ответ приходит ходом, оркестратор пересылает воркеру
через `send` и снимает блок.

**Стоп по бюджету.** Смотритель видит перерасход (раздел 6) -> `longrun halt` -> диалог
человеку с отчетом: сколько потрачено, кто сколько ходов сделал за час, что сейчас в doing.
Человек снимает `longrun resume` или из диалога.

**Контекст оркестратора.** Он читает компактные файлы состояния, не транскрипты, поэтому
растет медленно. Окно автокомпакции и хуки longrun обслуживают его так же, как воркеров.

Спрашивалка (реализована, раздел 13): `longrun ask` и тул `ask` MCP-сервера `longrun mcp` показывают диалог через
`osascript` из собственного процесса (`display dialog` / `choose from list`, сам выходит на передний план, звук; Focus режет
уведомления, а не окна). Спросивший ждет ответ до `ask_wait_sec` (90 с) и получает его сразу; позже ответ приходит ходом
в сокет сессии (или в inbox), диалог держит отвязанный процесс. Тул `notify(text)` для сообщений без ответа.

## 5а. Факты извне: доставка и фиксация

Доставка, оба канала проверены 2026-09-08:

- человек пишет прямо в чат оркестратора, даже пока тот работает: сообщение встает в
  очередь и приходит модели между вызовами инструментов (в транскрипте это вложение
  `queued_command`), а не после конца хода;
- любая сессия, скрипт или смотритель шлет `longrun send` в сокет: занятый оркестратор
  получает его между вызовами инструментов (проверено отправкой самому себе посреди
  хода), спящий начинает ход.

Фиксация, чтобы решение не зависело от памяти модели: команда
`longrun fact "текст" [--task T7] [--source review|msngr|user|watch]`:

1. пишет запись вида fact в `board.json` (источник, время, задача, handled=false) и
   строку в журнал;
2. если указана задача, ее воркер увидит `NEW FACT for T7` в дайджесте на следующем
   событии;
3. будит оркестратора (сокет, если жив; иначе inbox).

Дайджест оркестратора показывает `FACTS unhandled` на каждом пробуждении, пока оркестратор
не распорядится: `longrun fact ack <id> "что решил"` (переслал воркеру, поменял доску,
спросил человека, или "принято, действий нет"). Необработанный факт не исчезает из вида.
Факты с долгой жизнью оркестратор переносит в общие заметки (`add --shared -t fact`),
остальные архивируются через N дней после ack.

Факт, вкинутый словами в чат без команды, оркестратор по протоколу роли сначала фиксирует
через `longrun fact --source user` и только потом решает. Дайджест напоминает об этом
счетчиком необработанных фактов.

Автоматические источники, это правила смотрителя (ноль токенов в ожидании):

- `msngr <chat_id>`: `msngr-mcp cli read-new --chat-id ...` отдает только пришедшее с
  прошлого вызова, курсор локальный; новое -> `longrun fact --source msngr`;
- `pr-comments <id>`: у `arc pr` команды для комментариев нет, нужен REST Arcanum с
  OAuth-токеном (не проверено) либо проверка из сессии воркера через MCP devtools;
- `pr-status` и `pr-merged` уже есть, их срабатывание тоже идет через `fact`.

Смотритель не решает, важен ли факт: фиксирует и будит. Чтобы не будить на каждое сообщение
чата, у правила есть `--wake-on <regex>`: без совпадения факт ложится в inbox и ждет
следующего пробуждения.

## 6. Бюджет 5-часового окна

По умолчанию выключено (`budget_on: false`; включает `longrun budget on`, а `orchestrate start`
предлагает это, когда одно окно начинают делить несколько сессий). Политика: план `pace`
процентов в час (по умолчанию 20 = все окно за 5 часов), допуск `factor` (1.5). Смотритель на каждом тике сравнивает `used%` с `прошло_часов * pace`;
превышение в `factor` раз после первых 30 минут окна -> `halt` + диалог + отчет. Расход
считается на аккаунт, а не на проект, поэтому это глобальное правило смотрителя, а не
свойство оркестратора.

Откуда брать `used%`, по убыванию надежности:

1. `rate_limits.five_hour.used_percentage` и `resets_at` из JSON строки статуса.
   Документировано, но строка статуса живет в терминальном UI, а приложение запускает CLI
   как `--output-format stream-json --input-format stream-json`, без TUI. Скорее всего в
   приложении команда statusLine не выполняется; проверить один раз скриптом-логгером.
2. Эндпоинт `https://api.anthropic.com/api/oauth/usage` с токеном из Keychain
   (`Claude Code-credentials`, поле `claudeAiOauth.accessToken`, заголовок
   `anthropic-beta: oauth-2025-04-20`). Не документирован, но проверен 2026-09-09: отвечает
   `five_hour` и `seven_day`, в каждом `utilization` (проценты, число с точкой) и `resets_at`
   (ISO-8601 с зоной). Это и есть источник в реализации: смотритель читает токен через
   `/usr/bin/security` после разового "Always Allow" в диалоге Keychain, опрос раз в 5 минут,
   токен не пишется никуда.
3. Оценка по транскриптам всех сессий: сумма новых входных, кэш-записи и выходных токенов за
   окно. Единица не совпадает с процентами лимита, но темп "в полтора раза быстрее плана"
   по ней видно; калибруется по показаниям `/usage`.

Встроенное поведение Claude Code при исчерпании (`autoContinueAtUsageLimit`, уведомления
`quota_auto_resume_*`) работает уже после удара о лимит, задачу "остановить заранее" не
решает.

## 7. Проверено и не проверено

Проверено (документация или живьем на этой машине, 2026-09-08):

- слэш-команда в сообщении другой сессии не выполняется, приходит текстом; сообщение не
  может ничего подтвердить и не может менять настройки;
- приложение запускает CLI в режиме stream-json с `--permission-prompt-tool stdio`;
- транскрипт хранит `usage` каждого ответа, контекст считается точно; у этой сессии после
  компакции 99k токенов при окне 1M у Fable;
- дерево процессов: инструмент Bash это дочерний процесс `claude` сессии, pid сессии лежит
  в `~/.claude/sessions/<pid>.json` и в `claude agents --json`;
- PreToolUse умеет `permissionDecision: deny` с причиной, которую видит модель;
  UserPromptSubmit умеет `additionalContext`;
- окно автокомпакции: `/autocompact <tokens>` (сохраняется в настройках), флаг
  `--autocompact`, переменная `CLAUDE_CODE_AUTO_COMPACT_WINDOW`; по умолчанию компакция у
  границы окна модели;
- `claude --bg "prompt"`, `claude agents --json`, `claude attach|logs|stop|respawn`,
  состояние в `~/.claude/jobs/<id>/state.json`;
- типы уведомлений `permission_prompt` (после ~6 с ожидания), `idle_prompt` (60 с после
  ответа), `agent_needs_input`, `quota_auto_resume_*`; событие `PermissionRequest`;
- эндпоинт usage отдает данные по локальному токену (проба пользователя 2026-09-09: 5h 11%,
  неделя 42%; чтение Keychain из сессии агента классификатор блокирует, поэтому пробу и первый
  `longrun budget check` запускает человек);
- сообщение в сокет занятой сессии приложения приходит модели между вызовами
  инструментов (отправка самому себе посреди хода), очередь приложения доставляет
  вложением `queued_command` так же;
- `msngr-mcp cli read-new --chat-id` читает новое из чата из терминала, без MCP.

Не проверено:

- срабатывают ли в приложении хуки `Notification` и `PermissionRequest` (в терминале да);
- запускает ли приложение statusLine (проверка через atime не сработала: том не обновляет
  atime при чтении);
- прерывает ли убийство дочернего процесса инструмент чисто в приложении;
- таймаут MCP-тула для блокирующего диалога;
- `spawn_task` для проектов без git (например `shop` - папка хранилища Obsidian, проект без git).

Проба эндпоинта, токен в вывод не попадает:

```bash
python3 -c 'import subprocess,json,urllib.request;t=json.loads(subprocess.run(["security","find-generic-password","-s","Claude Code-credentials","-w"],capture_output=True,text=True).stdout)["claudeAiOauth"]["accessToken"];r=urllib.request.urlopen(urllib.request.Request("https://api.anthropic.com/api/oauth/usage",headers={"Authorization":"Bearer "+t,"anthropic-beta":"oauth-2025-04-20"}),timeout=15);print(r.read().decode()[:800])'
```

## 8. Чего не делаем и почему

- Agent teams Claude Code: одна команда на сессию, лид фиксирован, тиммейты живут внутри
  процесса лида и не переживают resume, нет командного уровня проекта. Не подходит для
  долгоживущих сессий приложения, живущих днями. Внутри одного воркера для параллельной
  подзадачи использовать можно.
- Опрос по таймеру (`/loop`, CronCreate) как основной цикл: каждое пробуждение стоит
  токенов, а событий между тиками часто нет. Только как страховочный heartbeat раз в
  30-60 минут через `longrun watch`.
- Чтение транскриптов воркеров оркестратором: раздувает его контекст.
- Все вопросы человеку только через оркестратора: решено иначе, диалог доступен любой
  сессии. Чтобы не было спама, воркер зовет `ask` сам только когда ждать нельзя (нужно
  действие человека прямо сейчас: подтверждение, доступ, сообщение кому-то), а вопросы по
  цели и приоритетам ставит на доску через `block`, их собирает оркестратор.

## 9. Этапы

1. Только longrun, без нового MCP: доска, роль и замок оркестратора, телеметрия в SESSIONS
   (контекст, ход, инструмент, повторные FAIL), события воркеров оркестратору, `fact` и
   `fact ack`, `halt` и `resume`, правило про затыки в смотрителе, рекомендация по окну

## 13. Реализовано: этап 2, спрашивалка (2026-09-09, версия 0.4.0)

Без нового бинаря: диалог и MCP-сервер живут в том же скрипте `longrun`.

- `longrun ask "вопрос" [--options "Да,Нет"] [--default Да] [--text] [--title T] [--wait SEC] [--expire MIN] [--icon note|caution|stop]`: диалог через `osascript` из собственного процесса (без разрешения Automation, сам выходит на передний план, проверено 09.09.2026; звук `beep`; Focus режет уведомления, а не окна). До трех вариантов - кнопки `display dialog`, больше - список `choose from list`, `--text` добавляет поле ввода. Вопрос записывается в `<сессия>/asks.json` (`Q<n>`, состояние pending/answered/cancelled/expired/failed) и в журнал; диалог держит отвязанный процесс (`ask _wait`, setsid, вывод в `~/.claude/longrun/ask.log`).
- Ответ: спросивший ждет `ask_wait_sec` (90 с) и получает строку `ANSWER Q3: Да; text: ...` сразу. Не дождался - печатает `PENDING Q3`, снимает claimed, и ответ приходит ходом: в сокет сессии (ход начинается даже посреди хода), иначе в inbox, откуда его отдаст следующий хук. Esc или кнопка Cancel -> `CANCELLED`, истек `--expire` (360 мин) -> `EXPIRED`, нет osascript или фикстуры -> `FAILED`; во всех трех случаях текст просит не переспрашивать, а решить самому или поставить `board block`. Неотвеченный вопрос в проекте с HQ ложится в ledger пунктом на пользователе; прежняя семантика `ask` (ledger + отчет, без диалога) сохранена флагом `--ledger`.
- `ask ls` и `ask answer Q3 "..."` (диалог пропал после перезагрузки, пользователь ответил в чате).
- MCP-сервер `longrun mcp`: stdio JSON-RPC без зависимостей, тулы `ask` (те же поля: question, options, default, free_text, title, wait_sec, expire_min, icon) и `notify`. Сессию находит по pid родителя в `~/.claude/sessions/<pid>.json` (сервер - дочерний процесс `claude`), проект - по индексу сессии, иначе по cwd; без проекта показывает диалог и ждет ответ инлайн. Регистрирует `install.sh`: `claude mcp add --scope user longrun -- ~/.local/bin/longrun mcp`; сервер появляется в сессиях, запущенных после регистрации. По документации таймаут MCP-тула по умолчанию 28 часов, idle-таймаут stdio-сервера 30 минут, а вызов дольше 2 минут в интерактивной сессии уходит в фоновую задачу; поэтому `wait_sec` ограничен 1500 с, а поздний ответ в любом случае приходит сообщением.
- Телеметрия: флаг `asking the user Q3 12m` в строках SESSIONS, блок `ASKED, waiting for the user` в дайджесте спросившего, флаг `ask` у смотрителя (вопрос без ответа дольше `stuck_wait_min` -> `STUCK?` оркестратору).
- Halt: тулы `mcp__longrun__*` не запрещаются (спросить пользователя - способ снять стоп). Бюджетный стоп показывает и диалог `STOP by longrun budget` с кнопками Keep stopped / Resume all: Resume all снимает halt, усыпляет правило до сброса окна и сообщает оркестраторам всех проектов; из тика смотрителя диалог запускается отвязанным процессом, тик не ждет.
- Тесты: `tests/ask.sh` (30 проверок): фикстура `LONGRUN_ASK_FIXTURE=<json>` вместо диалога, `LONGRUN_ASK_FIXTURE_DELAY` для позднего ответа, `LONGRUN_NO_UI=1` во всех наборах, чтобы тест никогда не показал настоящий диалог или уведомление.

Не вошло: этап 4 (автоматические источники фактов). Проверено живьем 09.09.2026 23:00 из сессии приложения: `longrun ask ... --wait 0` показал диалог поверх окон, ответ ушел в сокет и пришел в сессию как cross-session-message от 'longrun ask' посреди вызова Bash; процесс диалога завершился сам, в asks.json state=answered, delivered=socket. Не проверено живьем: диалог из тика launchd и автоматический перевод долгого вызова `ask` в фоновую задачу в приложении.
